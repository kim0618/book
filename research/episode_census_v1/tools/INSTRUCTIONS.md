# 에피소드 지도 조사 지침 (조사자 전용)

## 배경
사용자 한 명이 약 1년 동안 ChatGPT·Claude와 함께 여러 개인 프로젝트(사이트, 블로그, 자동매매, 게임, 앱, 책 등)를 진행했다. 이 대화로 일반 독자용 경험 논픽션을 쓸 예정이다. 지금 단계는 원고가 아니라 **에피소드 지도** 작성이다. 원문을 다시 요약하는 것이 목적이 아니라, 여러 원본 구간(E#####)을 실제 사건 단위로 묶고 원문 위치(사건 ID + 메시지 번호)로 추적 가능하게 만드는 것이 목적이다.

## 입력 형식
묶음 파일은 원본 구간의 축약본이다. 원문 전체가 아니다(긴 메시지는 `…[n자 생략]…`으로 잘림).
- `### E01394 | chatgpt | 시작~끝 | 분류/프로젝트코드 | title=대화 제목`
- `[76|U] 본문` = 메시지 번호 76, 발언자. U=사용자, GPT=ChatGPT, CW=Claude 웹, CC=Claude Code, CX=Codex, S=시스템.
- `⟦…⟧`는 가림 표식이다. 가림 안의 실제 값을 추측하거나 복원하지 않는다.
- 사용자가 다른 AI의 답변을 붙여넣은 경우에도 발언자는 U다. 붙여넣은 내용의 원 작성자를 언급할 때는 "사용자가 붙여넣은 ChatGPT 답변"처럼 구분한다.

## 할 일
1. 묶음 파일 전체를 처음부터 끝까지 읽는다(여러 번 나눠 Read). 일부만 읽고 끝내지 않는다.
2. 모든 구간 ID를 `segments`에 빠짐없이 기록한다.
3. 실제 사건 단위로 `episodes`를 만든다.

### 에피소드 단위 기준
- 하나의 실제 사건 = 하나의 목표를 둘러싼 시작→전개→결과(또는 중단)의 흐름.
- 같은 사건의 후속 대화, 반복 수정, 기술 로그, 재검증은 **같은 에피소드에 통합**한다. 독립 에피소드로 쪼개지 않는다.
- 같은 대화 안에서도 주제가 완전히 바뀌면 다른 에피소드로 나눈다.
- 다른 대화라도 같은 사건이 이어진 것이 원문으로 확인되면(같은 작업을 이어서 말함, 이전 결과를 붙여넣음 등) 같은 에피소드로 묶는다.
- 중요도가 낮아 보여도 버리지 않는다. 작은 사건도 에피소드로 남기거나, 사건이 아니면 segments에 상태와 라벨을 남긴다.
- 특히 놓치지 말 유형: 프로젝트 시작 / 아이디어 구체화 / 첫 완성·출시 / AI의 잘못된 지시·판단 / ChatGPT와 Claude의 다른 판단 / 예상치 못한 문제 / 사용자가 AI에 반대하거나 결정을 바꿈 / 여러 번 수정·재검증 끝의 해결 / 운영·수익화 / 성공한 작업 / 중단·방향 전환 / 사용자의 AI 사용 방식 변화.

### segments 상태값
- `EP`: 에피소드에 속함(`ep`에 에피소드 key, 여러 개 가능)
- `PRESERVE`: 사건이라 보기 어려운 단순 문답·개념 질문(예: 일반 프로그래밍 문법 질문). 라벨만 남긴다.
- `NOT_EP`: 빈 대화, 테스트, 시스템 자료, 또는 **회사 업무·사생활로 보이는 내용**(라벨은 "회사 업무 가능성" / "사생활 가능성"만 쓰고 내용은 적지 않는다).
- `UNVERIFIABLE`: 가림·생략 때문에 내용을 확인할 수 없음.
- `label`: 20자 안팎의 내용 라벨. 실명·가림 값 추측 금지.

### 사실성 규칙(엄격)
- 축약본에서 확인되는 것만 쓴다. 확인 안 되면 "확인 불가"라고 쓴다.
- 발언·행동·생각·결과를 창작하지 않는다. AI가 "완료했다/통과했다"고 말한 것은 "AI가 완료를 보고함"으로 쓰고 실제 결과로 단정하지 않는다.
- 사용자가 직접 코드를 읽거나 검토했다고 쓰지 않는다(사용자는 AI 결과를 확인·질문·지시한 사람으로 기술).
- ChatGPT·Claude 웹·Claude Code·Codex 발언자를 혼동하지 않는다.
- 다른 묶음에 있을 법한 연결은 `links`에 `"status":"미확정"`으로만 적는다.

### 인용(key_messages) 규칙
- 사건의 시작, 방향 전환, 오류 발견, 해결, 사용자 반응, 결과에 해당하는 실제 발언을 고른다. 에피소드당 보통 2~8개, 긴 사건은 더 많아도 된다. 사용자(U)의 핵심 반응을 빼지 않는다.
- `q`는 축약본에 보이는 원문을 **글자 그대로** 복사한 연속 부분 문자열(15~250자). 맞춤법·띄어쓰기·말투를 고치지 않는다. `…[n자 생략]…` 경계를 넘지 않는다. 요약문을 인용처럼 쓰지 않는다.
- `e`=구간 ID, `n`=메시지 번호(정수), `sp`=U/GPT/CW/CC/CX/S.

### 개인정보
- 사람 이름, 회사명, 실제 사이트·서비스명, 계정, 저장소명, 이메일, 전화번호를 새로 쓰지 않는다. 가림 표식(⟦사이트A⟧ 등)과 프로젝트 코드만 사용한다.
- 원문 인용 안에 사용자의 실명(예: 이름 두 글자)이 보이면 그 인용은 고르지 않는다.

## 출력
지정된 경로에 JSON 하나를 Write로 저장한다(UTF-8, 유효한 JSON). 형식:

```json
{
  "chunk": "W01",
  "segments": {"E00001": {"s": "EP", "ep": ["W01-01"], "label": "Vue 체크리스트 오류 문의"}},
  "episodes": [
    {
      "key": "W01-01",
      "title": "무슨 일이 일어났는지 알 수 있는 구체적 제목",
      "project": "EVENTS 프로젝트 코드(SITE_TAROT 등) 또는 OTHER",
      "start": "YYYY-MM-DD", "end": "YYYY-MM-DD",
      "background": "시작 배경 1~2문장",
      "goal": "사용자의 실제 목표 1문장",
      "process": "전개 2~5문장(구간 ID를 괄호로 표기)",
      "ai_actions": "AI의 제안·행동 1~2문장(어떤 AI인지 명시)",
      "user_reactions": "사용자의 실제 반응 1~2문장",
      "result": "확인 가능한 결과 또는 '확인 불가'",
      "state": "완료|중단|방향 전환|진행 중(묶음 끝 기준)|미확인",
      "types": ["프로젝트 시작", "AI 오판", "..."],
      "events": ["E00001", "E00002"],
      "key_messages": [{"e": "E00001", "n": 1, "sp": "U", "q": "원문 그대로", "role": "시작"}],
      "links": [{"hint": "연결 단서", "basis": "근거(구간·메시지 또는 설명)", "status": "확정|미확정"}],
      "unknowns": "확인되지 않은 것",
      "anon": "출판 시 익명화가 필요한 요소(가림 표식·유형으로만 표현)",
      "publish_flag": "출판 후보|회사 업무 가능성|사생활 가능성|투자 개인정보 주의"
    }
  ],
  "continues": "묶음 경계에서 다른 묶음으로 이어지는 에피소드 key와 설명, 없으면 빈 문자열"
}
```

- 에피소드 key는 `<묶음>-NN` 형식.
- 모든 구간이 segments에 있어야 하고, EP 구간은 해당 에피소드의 events에도 있어야 한다.
- 저장 후 검증 스크립트를 실행한다: `python3 -I /tmp/claude-0/-home-user-book/c49a03fe-2831-55b6-bd68-b9b23214366d/scratchpad/census/validate.py <묶음이름>`. 구간 누락, 연결 불일치, 인용 불일치(원문 전체와 대조), 발언자 불일치가 나오면 고쳐서 `OK`가 나올 때까지 반복한다. 인용 불일치는 인용을 고치거나 빼야 하며, 원문을 고쳐 맞추지 않는다.
- 마지막 답변은 짧게: 구간 수, 에피소드 수, 상태별 구간 수, 특이사항 2~3줄. 저장소 파일은 절대 수정하지 않는다.
